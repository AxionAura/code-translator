## 2. Product Goal

A serious developer tool that translates source code and complete multi-file projects between **Python, JavaScript, and TypeScript** (all 6 directions) while preserving behavior as accurately as technically possible — and that **honestly reports** what was translated deterministically, what was adapted semantically, what was ambiguous, and what was unsupported. It never presents an unvalidated translation as correct. Long-term: extensible to additional languages.

## 3. Current Scope

**Designed and approved for V1**:
- Single-file and project-level translation, 6 directions with a graded support matrix.
- Core construct matrix (expressions, control flow, functions, classes, exceptions, comprehensions, f-strings, slicing, generators, decorators-as-application, async syntax; explicit `unsupported` list: metaclasses, descriptors, `except*`, class-pattern `match`, threads, etc. — see `docs/language-support.md` §4).
- Dependency mapping registry v1 (~15 stdlib modules, `requests`→`fetch`, `pytest`→`vitest` basic).
- Validation pipeline (syntax → types → dependencies → build → tests → differential) with a "claim ladder".
- Bounded, AI-optional repair loop. CLI. Fixture + benchmark infrastructure. Sandboxed test execution.

**Explicitly deferred** (decisions D-002/D-013 in `docs/decisions.md`): no universal IR (a Semantic Layer replaces it — see §9/§16); **no GUI in V1** (CLI-first; web UI/VS Code extension deferred to V2 — documented deviation from the original "Basic GUI" V1 requirement).

## 4. Architecture

Target architecture (approved blueprint, `docs/architecture.md`):

```
Source Project
  → Project Analysis (ModuleGraph: imports, SCCs, topo order, entry points, tests)   [M3: implemented]
  → Parsing            [Python: CPython stdlib bridge (ast+symtable+tokenize→JSON), tree-sitter fallback]  [M1: implemented]
                       [JS/TS: oxc-parser, @babel/parser fallback]                    [M2: implemented]
  → Semantic Layer     (CommonType model, symbol/scope resolution, ModuleContracts)   [M3: implemented]
  → Lowering + Code Generation (per direction; TransformationLedger records EVERY decision as
      deterministic | semantic | ambiguous | unsupported)                             [M4: implemented for py→js/ts]
  → Dependency Mapping (in-repo registry + heuristics + AI proposals)
  → Test Translation   (pytest↔vitest, best effort)
  → Validation Engine  (S1 syntax → S2 types → S3 deps → S4 build → S5 tests → S6 differential; each
      stage = pass|fail|warn|skipped(reason); "claim ladder" caps what may be asserted)
  → Bounded AI-assisted Repair → Re-validation
  → Final Target Project + Reports (.ctrans/ ledger, source map, validation report, repair journal)
```

Monorepo layout: `packages/{core,parser-py,parser-js,codegen-js,codegen-py,registry,validator,sandbox,repair,ai}`, `apps/cli` (binary `ctrans`). Dependency direction acyclic (ADR D-017): `core` is the base type layer; implementation packages depend on core and strictly lower layers; `apps/cli` wires concrete implementations. Enforced by `scripts/workspace-boundaries.test.ts`.

## 10. Translation Pipeline

- **Current actual pipeline:** full M4+M5 chain is real for py→js/ts: `source → ParseResult → analyzeModule → SemanticModel`; `buildModuleGraph` orders units; async-boundary propagation when a sync-to-async module participates; lowering+emission with per-construct ledger entries (registry lookups injected via `RegistryLookup`); Prettier finalization; S1 re-parse + S2 whole-program oracle validation + S3 dependency validation (registry/graph verdicts); claim ladder + report. Test translation (7) and sandboxed execution (9) are M6+. **In project mode (M10) the validation chain continues**: S4 tsc/compileall build → S5 translated tests (flaky rerun-once) → S6 differential → S7 opt-in smoke, all assembled in canonical order and evidence-checked before the report is written. M9/M10 repair runs after validation: classify → propose one unit-scoped diff → re-run the caller's validators (translate: S1–S3; project: the real S1–S6) → accept only a strictly higher claim with required behavioral stages passing, or discard exactly. `PipelineResult` exposes the executed `validationStages` (details included) so repair classifies real evidence.
- **Determinism guarantee:** lowering, emission, formatting, and validation are deterministic with AI disabled (double-run equality is golden-tested). Sandboxed stages depend on wall-clock bounds and are reported honestly; the flaky policy records both attempts. With AI enabled only the ambiguity decision or a repair patch enters, and both re-enter deterministic validation; a rejected/failed AI path leaves the deterministic output byte-identical.
- **Per-unit detail (docs/translation-pipeline.md §2):** context = unit AST + direct-dep ModuleContracts (via cross-unit symbol kinds); helper import list is per-unit, runtime file content is the union (emitted once in `finalizeUnits`); barrel `__init__` modules re-export their `__all__`/public names.

## 11. AI Architecture

- **AI is used (implemented):** (1) `resolveAmbiguity` for engine-classified `ambiguous` constructs — must *choose among offered options*, never invent behavior (M8); (2) `proposeRepairPatch` in the bounded repair loop (M9) — unit-scoped unified diffs, grammar/scope/policy validated, re-validated by the engine, accepted only on strictly higher claim; (3) optional off-by-default idiom polish — **not implemented**.
- **AI is not used (implemented invariant):** parsing, symbol/type resolution, lowering, codegen, dependency registry lookups, validation verdicts. CI goldens never call AI.
- **Provider abstraction (implemented):** `ChatModel.complete()` interface; adapters for OpenAI-compatible endpoints (incl. Ollama/vLLM/llama.cpp), Anthropic, custom endpoints; secretlint-based hard gate before every request (including re-asks); caps (calls/tokens/USD/wall-clock) enforced in code; prompt payloads = unit context + direct-dependency contracts + bounded diagnostics, token-budgeted — whole-project prompts are impossible by construction. Repair adds one `AiBudget` per proposer, response cache, strict diff validation, and a hash-only journal.
- AI is OFF by default; a disabled or failing AI path degrades to the deterministic output (byte-identical) with typed warnings/stop reasons. Keys come from `CTRANS_AI_KEY` only.

## 15. Known Limitations

Intentional, documented V1 limitations (all produce loud warnings, never silent misbehavior — `docs/language-support.md` §4/§5):
- `unsupported` (M4): metaclasses, descriptors, `except*`/exception groups, `match` patterns (all), `assert`, `del`, decorators (functions/methods/classes), async generators, `__getattr__`, `eval`/`exec`/`compile`, threads/multiprocessing, C-extension stdlib modules, PEP 750 t-strings, **unmapped Python builtin calls (sorted/next/max/…)** — markers + `CTW-UNSUPPORTED-*` warnings; the unit still emits and the report counts it partially-translated.
- **Registry surface (updated M5):** mapped methods/builtins/modules lower through the registry (usage-tested); UNMAPPED methods still lower verbatim with `CTW-METHOD-UNMAPPED`, unmapped builtins stay `unsupported` with `CTW-UNSUPPORTED-CALL-BUILTIN`, and unmapped modules pass through verbatim with exact S3 warnings — the honest surface for everything the v1 registry does not cover.
- **String semantics (updated M5):** iteration, `len()`, indexing (incl. negative), lexicographic comparison, and slicing are all code-point-correct via the runtime helpers — astral-plane parity with Python is verified by tests. Raw JS string operations in handwritten target code still measure UTF-16 units (out of translation scope).
- **Float formatting (updated M5):** statically float-typed sites and non-integral numbers reproduce Python's repr exactly (`__ctrans_floatStr`); DYNAMIC integral numbers still print int-like in number mode (the int/float runtime distinction is lost — bigint mode is exact since Python ints are bigints there).
- **Dict key order:** iteration/print order of dicts with integer-like keys follows JS object property enumeration (integer-like keys first, numerically ascending) instead of Python insertion order; values are unaffected.
- **Test translation subset (M6):** the pytest→vitest mapper covers test functions, plain `Test*` classes (no `__init__`/bases/helper methods), assert patterns, same-module factory fixtures, `parametrize` with primitive literal cases, and `pytest.raises(E)` without `match=`/`as`. Outside the subset: `monkeypatch`/built-in fixtures, fixture scopes/autouse/params, conftest.py fixtures (the mapper's conftest context exists but project mode does not wire conftest translation yet), fixture-finalizers/yield fixtures, plugins — all reported `unsupported` with `CTW-UNSUPPORTED-*` and counted in the report.
- **Differential name rendering (M6):** S6 matches per-case names by string-rendered parametrize values (Python `str` vs JS `String`) — exact for numbers and strings, divergent for booleans (`True` vs `true`) and complex shapes; such cases are outside the level-5 golden surface and mismatch honestly when present.
- **Validation stage coverage (updated M10):** S2 type-checks the emitted SOURCE project only — emitted test modules are syntax/build-validated (S1/S4) plus executed (S5/S6); their vitest API surface is mapper-generated (fixed shapes). S4 is now wired for TypeScript/Python project output (JS has no build step); an EXECUTED S4 failure caps the claim at 3, while skipped S4 (no toolchain/JS/S1 fail) is non-blocking. S7 is outside the claim ladder by design.
- **M10 validation scope:** `translate`/`check` remain S1–S3 surfaces (no whole-project test/build context); S4/S7 and project repair run in `project` mode. Strict mode needs an operator-provided image containing node+python3 (and the toolchain mounted); pulls are disabled, so an unavailable image refuses rather than fetching. gVisor is detected but not exercised in CI; podman is wired/unit-tested but the real container test prefers docker. Project repair is single-unit, requires S5/S6 to be executable and passing on acceptance, and can still accept a semantic deletion that satisfies the evidence (claim-level acceptance is necessary, not semantic equivalence). A `validation-unavailable`/strict-infrastructure failure makes the CLI exit 1 with the baseline (or no output, for strict baseline refusal) untouched.
- **AI repair scope (updated M10):** `translate --repair` re-validates S1–S3; `project --repair` re-validates the real S1–S6 and refuses (`validation-unavailable`) when behavioral validation cannot run. Patches are strictly single-unit: a failure that needs a cross-unit change is not repaired. Acceptance proves monotone claim improvement plus required behavioral passes, not semantic equivalence; the policy guard can only block known suppression patterns. Each proposer carries one run-scoped `AiBudget`; cross-run caching is not implemented.
- **AI layer scope (M8):** ambiguity resolution + repair proposals are implemented; idiom polishing remains deferred. Credentials come from `CTRANS_AI_KEY` only — OS-keychain/file storage is M11 hardening. The CLI exposes the OpenAI-compatible and Anthropic providers; the custom templated endpoint is a library export (CLI flag wiring deferred). Cost caps enforce only when a provider reports USD; token accounting uses reported usage plus a documented chars/4 estimate otherwise. Cache is per-run (in-memory); cross-run persistence is not implemented (M11 benchmark scope). The ambiguous surface is currently Python `match` only — other documented-ambiguous constructs (e.g. global/nonlocal escapes) remain heuristic-only.
- **Reverse-direction subset (M7):** JS/TS → Python covers the constructs in language-support §5c; outside it (async function expressions in expression position, general `for(;;)` loops that are not counting patterns, `switch` fallthrough, computed class member keys, namespaces/enums/decorators/parameter properties/abstract classes, tagged templates, `arguments`, CommonJS `require`) is `unsupported`-loud with markers + `CTW-UNSUPPORTED-JS-CONSTRUCT`. `new Map()`/`Set` models are approximate (dict/unknown), and `String()`/template interpolation follows JS `toString` spellings through `__ctrans_str_js` (object interpolation → `[object Object]`). JS/TS → Python covers the constructs in language-support §5c; outside it (async function expressions in expression position, general `for(;;)` loops that are not counting patterns, `switch` fallthrough, computed class member keys, namespaces/enums/decorators/parameter properties/abstract classes, tagged templates, `arguments`, CommonJS `require`) is `unsupported`-loud with markers + `CTW-UNSUPPORTED-JS-CONSTRUCT`. `new Map()`/`Set` models are approximate (dict/unknown), and `String()`/template interpolation follows JS `toString` spellings through `__ctrans_str_js` (object interpolation → `[object Object]`).
- **Reverse validation scope (M7):** pyright S2 runs on the materialized output project; S5/S6 for Python output require vitest→pytest test translation, which the M7 roadmap defers — reverse runs therefore cap at claim level 3 (S1+S2+S3) and say so. Reverse behavior evidence comes from the sandboxed differentials and round-trip test, not from translated tests.
- **Registry v1 boundaries (M5):** `sorted`/`min`/`max`/`enumerate`/`next` kwargs forms outside the call surface; `reversed`/`zip`/`range` materialize (documented); `random` does not reproduce CPython's Mersenne Twister value-for-value; `json.dumps` allow_nan emits `null` for non-finite floats (Python emits `Infinity` literals); `math`/`json`/`sys`/`random` surface is the mapped subset (the full stdlib is M6+ registry scope); `requests` sessions/proxies/auth/`data=`/`json=` kwargs unsupported-loud; `pathlib`/`datetime`/`re`/`itertools`/`functools`/`enum`/`dataclasses`/`typing`/`abc`/`logging`/`statistics`/`decimal` remain unmapped (reported, never guessed).
- **Loop variables after their loop:** `for` targets keep JS block scoping — post-loop use is S2-flagged (out of scope), and C-style range loops already diverge on the post-loop value (last-yield vs end).
- **Helper-dense dynamic code:** statically unknown operands route through `__ctrans_` helpers (D-023); the M5 provability analyzer will thin them where types prove equivalence — `a + b` on unknowns is correct but not idiomatic.
- **Mutability/identity divergences (documented per construct):** Python default args share one object (M4 re-evaluates per call — the footgun deliberately not reproduced); tuples → arrays (immutability lost, warning); dict keys stringify; class attributes → static (instance access via class name only).
- Sync→async propagation (e.g., `requests`→`fetch`) changes public signatures — reported per-signature (M5 rewire).
- Python grammar range 3.12–3.14; tree-sitter fallback is explicitly lower-fidelity.
- JS→TS emits honest `unknown`s, not invented types; Python/JS CommonType inference is deliberately conservative (literals, common containers, annotations) — everything dynamic is `unknown`.
- Registry v1 covers a fixed module list (M5); unmapped third-party deps are reported, never guessed.
- Full-fidelity int arithmetic requires `intMode=bigint`; default `number` mode warns on precision-risky patterns (int annotations, bitwise).
- CLI executable runs from TS sources via Node type stripping (`apps/cli/bin/ctrans.mjs` with a `.js`→`.ts` resolve hook), hence `engines >= 22.18`; compiled dist entry still deferred.
- No build/dist emission yet (deliberate); packages resolve via `exports -> src/index.ts` under `tsc --noEmit`.
- ESLint is non-type-aware for now; Prettier deliberately excludes `*.md` and `tests/fixtures/**`.
- `parse(source: string)` transports decoded text as UTF-8: non-UTF-8 source files must be decoded by the caller (project intake, M6).
- Python front-end verified on 3.14.8; 3.12/3.13 accepted by the handshake but not exercised here.
- oxc depth screen: nesting above 2000 rejected with a typed limit error (D-020).
- ModuleGraph resolution is against the analyzed file set only — no tsconfig paths, no namespace packages (bare `from . import x` needs a package `__init__.py` — verified in the audit), `importlib` dynamic imports untracked (approximate).
- Semantic `this`-binding and TDZ semantics are not yet modeled (documented; needed before JS→X codegen claims).
- Remaining codegen-js uncovered lines (90.21% vs 100%) are unsupported-arm minutiae and type-inference fallthroughs — meaningful-behavior tests, not a floor gap (see §12).

## 16. Failed Approaches (researched and rejected, with reasons)

- **Universal intermediate representation** — rejected for D-002 reasons; the strongest prior art does not use one.
- **Embedding pyright internals as a library** — no public API; unstable between releases; pinned CLI + JSON instead.
- **TypeScript 7 (tsgo) as semantic engine** — verified: 7.0 ships no JS API. Pinned `typescript@6` behind an adapter instead.
- **js2py as JS-execution substrate** — unpatched sandbox-escape RCE (CVE-2024-28397); unmaintained.
- **trufflehog for secret scanning** — AGPL-3.0; embedding license risk. secretlint (MIT) chosen.
- **semgrep / GitHub `semantic` as rewrite substrate** — LGPL + scan-oriented; archived respectively.
- **firejail / systemd-run for sandboxing** — suid-root CVE history; non-root cannot isolate network.
- **Pyodide for validation execution** — not a security boundary; cannot run subprocess-using test suites.
- **LLM-as-translator architecture** — verified ~26.65% naive correctness; deterministic-first + escalation instead.
- **ts-migrate-style JS→TS (blanket `any`)** — dishonest types; our JS→TS emits `unknown` + diagnostics instead.
- **Recursive AST walkers for hostile input** — M2/M3 convert everything to explicit-stack iteration after the oxc segfault finding; recursion is only safe where depth is bounded by construction (Python's parser depth guard).

## 17. Security

Model (`docs/security.md`): local-first; user code is untrusted data; parsing never executes (Python bridge imports only stdlib `ast`/`symtable`/`tokenize` on the file's *syntax*, never user modules); semantic analysis and module resolution are pure data operations; all execution (S4–S7 where code/tools process untrusted output) through `@ctrans/sandbox` with no network by default, timeouts, output caps, temp cwd, env whitelist. **M10 strict mode:** Docker/Podman runs use daemon-checked detection, an explicit image, `--pull=never`, `--network none`, read-only rootfs, `--cap-drop ALL`, no-new-privileges, cgroup limits, workspace-only rw mount, read-only toolchain mounts, no host env/socket, and cidfile cleanup; missing runtime/image or requested-but-unavailable gVisor is a hard refusal, never a host fallback. S7 harness files are workspace-relative, size/count capped, and only the verdict is persisted. **M9 repair security:** the journal is hash-only at a fixed path (no diffs/prompts/responses/source; 0600; containment-checked; corrupt data preserved aside), unit-scoped diffs cannot touch tests/configs/other files/generated artifacts, a policy guard rejects validation/lint/test suppression, and the engine re-runs real validators before anything is written; project repair additionally requires passing S5/S6. Secret-scan hard gate before any AI request; keys via `CTRANS_AI_KEY` only (keychain/file is M11); never run installs of translated projects without explicit consent; model output is data, never commands. Known concerns: bwrap unavailable on hardened kernels (capability-detected, stages skipped); npm supply-chain risk mitigated by lockfile pinning + pnpm script-blocking; claim-level acceptance cannot prove semantic equivalence (S5/S6 are the behavioral evidence).
